# Reproducible builds

What each release artifact is, whether you can rebuild it bit for bit from the
tag, and how to check. Written for #487 and verified on 2026-09-25. A "no" is
recorded with its cause, not hidden.

Every release is built by [`.github/workflows/release.yml`](../../.github/workflows/release.yml)
from a `vX.Y.Z` tag. Run the commands below from a clean checkout of that tag.

| Artifact | Reproducible | How to verify |
|---|---|---|
| `openrisk-linux-amd64` (backend binary) | **Yes**, checked on every release | See below |
| `frontend-dist.tar.gz` | No | Compare the extracted files, not the archive |
| `openrisk-X.Y.Z.tgz` (Helm chart) | No | Compare the extracted files, not the archive |
| `ghcr.io/opendefender/openrisk:X.Y.Z` (image) | No | Pull by the digest printed in the release notes |
| `openrisk-*-X.Y.Z.cdx.json` (SBOMs) | Content yes, bytes no | Compare the component lists |
| `SHA256SUMS` | Follows from the files it lists | `sha256sum -c SHA256SUMS` |

## Backend binary: yes

`make build` compiles with `CGO_ENABLED=0 -trimpath` and stamps only the version
and the commit (`-X main.Version`, `-X main.Commit`). Go also embeds the commit,
its time and a clean-tree flag, all of which come from the tag. Nothing depends
on the build machine, its paths or the clock.

The release enforces it. The `reproducibility` job checks the tag out twice, in
two directories, builds each with its own empty `GOCACHE`, and fails if the two
`sha256` differ. The publish job then fails if the binary it is about to attach
differs from those two builds.

To check a release yourself, with the Go version the release used (printed by
`go version -m openrisk-linux-amd64`):

```sh
git clone --branch vX.Y.Z https://github.com/opendefender/OpenRisk.git
cd OpenRisk
make build
sha256sum backend/openrisk            # compare with the line in SHA256SUMS
go version -m backend/openrisk        # go1.25.x, -trimpath=true, vcs.modified=false
```

Two clean clones of commit `b3b9bc7`, each built with its own empty cache on
Go 1.25.13, both gave `e8b5d0ecba4765bd12bd71785bf5aeb713b00aa9894cb817e41a862ec942bf74`.

A different Go patch version gives a different binary. Build with the same one.

## Frontend archive: no

`frontend-dist.tar.gz` is made with plain `tar -czf`. Tar records each file's
modification time, which a fresh checkout and build set to "now", and gzip
records a timestamp in its header. The archive differs on every build even when
its content does not.

Whether `frontend/dist` itself is identical across two `npm ci && npm run build`
runs has not been checked. To compare, extract the archive and diff the tree
against your own build:

```sh
mkdir released && tar -xzf frontend-dist.tar.gz -C released
cd frontend && npm ci && npm run build && cd ..
diff -r released/dist frontend/dist
```

## Helm chart: no

`helm package` stores each file's modification time in the archive. Packaging
the same directory twice gives the same file, but packaging two checkouts of
the same commit does not, because a checkout sets every mtime to the time it
ran. Tested on 2026-09-25: two copies of `helm/openrisk` with different mtimes
gave two different `.tgz`. Compare the extracted files:

```sh
mkdir released && tar -xzf openrisk-X.Y.Z.tgz -C released
diff -r released/openrisk helm/openrisk
```

## Container image: no

The root `Dockerfile` installs Alpine packages with `apk add` at build time, so
a rebuild picks up whatever the Alpine mirror serves that day. Docker also
records build timestamps in the image config. A rebuild from the tag gives a
different digest.

What the release does guarantee is that the image published is the image that
was scanned. It is built once, gated, saved as a tarball, and that tarball is
what gets pushed. Pull it by the digest in the release notes, not by the tag:

```sh
docker pull ghcr.io/opendefender/openrisk@sha256:<digest from the release notes>
```

## SBOMs: same content, different bytes

The three CycloneDX files are generated by Trivy. Each run writes a random
`serialNumber`, the current time in `metadata.timestamp`, and random UUIDs as
`bom-ref` for some components, so no two runs are byte-identical. The components
listed are the same. Tested on 2026-09-25: two runs on the same tree gave the
same 161 backend and 160 frontend package URLs.

```sh
trivy fs --format cyclonedx --output backend.cdx.json backend
diff <(jq -r '.components[].purl' openrisk-backend-X.Y.Z.cdx.json | sort) \
     <(jq -r '.components[].purl' backend.cdx.json | sort)
```

Use the Trivy version pinned in `release.yml` (`TRIVY_VERSION`). The image SBOM
describes the published image, which is not reproducible (see above), so check it
against the image pulled by digest.
