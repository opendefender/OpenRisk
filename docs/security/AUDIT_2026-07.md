## Scope 1 — Hachage des mots de passe

**Verdict : l'affirmation du README est VRAIE. Aucune migration nécessaire.**

Le chemin de production (`POST /auth/register`, `POST /auth/login`) et le seeder de l'admin initial hachent tous en **Argon2id** :

- `internal/auth/password_hasher.go` — `Argon2idPasswordHasher` (via `golang.org/x/crypto/argon2` `IDKey`).
- `cmd/server/main.go:506-508` — `NewLoginUseCase(...)` / `NewRegisterUseCase(...)` reçoivent `NewArgon2idPasswordHasher()`.
- `internal/handler/user_handler.go:122-124` — le seeder admin hache aussi en Argon2id.

Paramètres actuels (`password_hasher.go:28-34`) : `memory=65536` (64 MB) ✓, `threads=4` ✓, `keyLen=32` ✓, `saltLen=16` ✓, `time=2`.

### S1-1 — Argon2id iterations=2 (spec : 3) · Faible (durcissement)
`time=2` est conforme OWASP à 64 MB, mais la spec d'audit demande explicitement `iterations=3`. Alignement trivial.

### S1-2 — `Verify()` non constant-time · Faible · CVSS 3.1 (`AV:N/AC:H/PR:N/UI:N/S:U/C:L/I:N/A:N`)
`password_hasher.go:92-93` compare les hachages avec l'opérateur `==` **malgré un commentaire affirmant « constant-time »**. Side-channel temporel (difficile à exploiter via le réseau, mais le commentaire est mensonger). **Correctif** : `crypto/subtle.ConstantTimeCompare`.

### S1-3 — Énumération d'utilisateurs par timing · Faible · CVSS 3.7 (`AV:N/AC:L/PR:N/UI:N/S:U/C:L/I:N/A:N`)
`internal/application/auth/login.go:77-93` : pour un email inexistant, le use case retourne **avant** d'exécuter le Verify Argon2 (coûteux). La différence de temps de réponse crée un oracle d'énumération. Les messages d'erreur sont, eux, déjà génériques (« invalid credentials »). **Correctif** : exécuter un hachage « leurre » (dummy verify) quand l'utilisateur est absent pour égaliser le temps.

### S1-4 — Code mort (SHA256 + bcrypt) · Info
`SimplePasswordHasher` (SHA256, `password_hasher.go:149+`) est neutralisé (`Hash` renvoie une erreur, `Verify` renvoie `false`). `MultitenantAuthService.Login` (bcrypt, `multitenancy_auth_service.go:85`) n'est routé sur aucun endpoint vivant (voir S2-2). À supprimer.

## Scope 2 — Secrets & credentials

**Verdict : aucun secret réel dans l'historique.** Aucun `.env`/`.pem`/clé jamais commité (`git log --all --diff-filter=A`). Les clés RSA du JWT sont chargées via env/fichier avec **panic si absentes** (`pkg/auth/rsa.go:41`) — pas de clé en dur. `.env.example` ne contient que des placeholders. Le hit « BEGIN PRIVATE KEY » de l'historique est un **placeholder d'UI** (`frontend/src/features/infrastructure/scannerMeta.ts:72`), bénin.

### S2-1 — Fallback `admin123` fail-open · Moyen · CVSS 8.1 conditionnel (`AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:H/A:N`)
`internal/handler/user_handler.go:110-120` : le garde de production (`log.Fatal` si `INITIAL_ADMIN_PASSWORD` absent) ne se déclenche **que** si `APP_ENV == "production"` exactement. Un déploiement avec `APP_ENV` vide, `prod`, ou `staging` **seed silencieusement `admin123`** (mot de passe publiquement connu). **Correctif** : *default-deny* — n'autoriser le fallback que si `APP_ENV == "development"`, sinon `log.Fatal`.

### S2-2 — HS256 legacy + secret `"deprecated"` · Moyen (landmine) · CVSS 3.7 actuel / 9.8 si atteignable
`internal/config/config.go:57-59` : si `JWT_SECRET` est vide, il vaut la chaîne codée en dur **`"deprecated"`**. `internal/service/auth_service.go` et `multitenancy_auth_service.go` signent des jetons en **HS256** avec ce secret. Ces chemins sont **non atteignables** aujourd'hui (le gate `AuthMiddlewareRS256` n'accepte que RS256 et rejette HS256 ; les routes `/auth/legacy/*` ont été retirées), mais si une route est un jour montée hors du gate avec ces services, un attaquant forge des jetons instantanément avec un secret connu. **Correctif** : supprimer les services HS256 legacy et le défaut `"deprecated"`.

### S2-3 — Placeholders Helm sans garde de boot · Faible · CVSS 4.0
`helm/openrisk/values.yaml` et `helm/values-prod.yaml` livrent `changeme` / `changeme-in-production` pour les mots de passe Postgres/Redis/admin. Aucune vérification de démarrage ne refuse ces valeurs. **Correctif** : refus au boot si un mot de passe critique appartient à une liste de valeurs faibles connues en production.

### S2-4 — `gitleaks` absent de la CI · Faible (process)
La spec exige un scan `gitleaks` de tout l'historique. **Correctif** : job CI `gitleaks` (`chore/ci-gitleaks`) + run complet documenté.

## Scope 3 — Isolation multi-tenant (point le plus critique)

**Mécanisme sain.** `internal/middleware/auth.go:80-112` : le gate RS256 rejette `claims.TenantID == uuid.Nil` (401) et pose le contexte tenant sur chaque requête (`tenant_id`, `SetContext(OrganizationID)`). La PR #159 a corrigé 6 fuites cross-tenant réelles et ajouté des tests ponctuels (`user_/team_/score_engine_/bulk_operation_isolation_test.go`).

### S3-1 — Pas de test d'isolation exhaustif généré depuis les routes · Élevé (assurance)
Il existe **4 tests d'isolation dédiés** + des assertions cross-tenant éparses, couvrant une fraction des **~301 routes** enregistrées dans `main.go`. Le risque existentiel d'un SaaS GRC (fuite cross-tenant) **n'est ni testé systématiquement ni bloquant en CI**. **Correctif** (`test/tenant-isolation-matrix`) : suite d'intégration paramétrée qui, pour chaque endpoint mutant/lecteur, crée les tenants A et B, s'authentifie en A, tente lecture/écriture/suppression sur les ressources de B (par ID, filtre, recherche, export, agrégat de dashboard) et **assert 403/404, jamais 200, jamais de fuite dans un compteur**. Exécutée live (Postgres+Redis), bloquante en CI.

### S3-2 — IDOR latent Marketplace · Moyen (latent) · CVSS 8.8 si activé
`internal/service/marketplace_service.go:229` (`First(&app, "id = ?", appID)`) et les méthodes `GetApp/UpdateApp/EnableApp/UninstallApp/UpdateAppSync/GetAppLogs` filtrent par `id` **sans `tenant_id`**. **Injoignable actuellement** : les tables Marketplace sont volontairement hors `AutoMigrate` (chaque route 500 sur table absente). **À corriger avant toute activation de la Marketplace.** Laissé documenté (correction propre cascaderait sur 8 sites internes non testables tant que le module est inactif).

## Scope 4 — Durcissement

### S4-1 — Bypass rate-limit via `X-Forwarded-For` · Élevé · CVSS 7.3 (`AV:N/AC:L/PR:N/UI:N/S:U/C:H/I:N/A:N`)
`internal/middleware/ratelimit.go:139-142` : la clé de throttle vaut `c.IP()` **sauf** si l'en-tête `X-Forwarded-For` est présent, auquel cas cet en-tête **fourni par le client** devient la clé, sans validation. Un attaquant fait tourner `X-Forwarded-For` à chaque requête → **compteur toujours à 1 → brute-force illimité** sur `/auth/login` et `/auth/register`. Le seul contrôle anti-brute-force du produit est ainsi **entièrement contournable**. **Correctif** : ne dériver l'IP client de `X-Forwarded-For` que derrière une liste de proxys de confiance (configurer `fiber.Config.ProxyHeader` + `TrustedProxies`, ou utiliser `c.IP()` seul).

### S4-2 — Headers de sécurité stricts non appliqués · Moyen · CVSS 5.3
`cmd/server/main.go:405` applique `helmet.New()` **avec ses défauts** (pas de `Content-Security-Policy`, pas de `Strict-Transport-Security`, `X-Frame-Options: SAMEORIGIN`). Le `SecurityHeadersMiddleware` maison (`security_hardening.go:73-109`), qui pose CSP + HSTS preload + Referrer-Policy + Permissions-Policy + `X-Frame-Options: DENY`, est **du code mort** (jamais appelé). **Correctif** : câbler `SecurityHeadersMiddleware` (avec CSP durcie, cf. S4-5) et vérifier les en-têtes live. *(À confirmer par observation des headers émis.)*

### S4-3 — Fuite d'erreur interne / SQL · Moyen · CVSS 5.3 (`AV:N/AC:L/PR:L/UI:N/S:U/C:H/I:N/A:N`)
`cmd/server/main.go:388-396` : l'`ErrorHandler` renvoie `"msg": err.Error()` **verbatim** pour toute erreur non-`*fiber.Error` (donc les 500). Une erreur GORM/`pq:` brute (ex. `duplicate key value violates unique constraint "..."`) est exposée au client, révélant schéma et requêtes. **Correctif** : message générique (`"internal server error"`) pour les 5xx en production, détail loggé côté serveur (avec `request_id`).

### S4-4 — Pas de rate-limit global ni par tenant · Moyen · CVSS 5.3
Seuls `/auth/login` et `/auth/register` sont throttlés (`main.go:560-568`). `/auth/refresh`, `/auth/logout` et les ~297 autres routes ne le sont pas. La spec demande un rate-limit **par tenant ET par IP**. `APIRateLimit()`/`PublicRateLimit()` existent mais **ne sont pas câblés**. **Correctif** : rate-limiter global par IP + par tenant (clé `tenant:%s` quand authentifié).

### S4-5 — CSP `script-src 'unsafe-inline'` · Faible · CVSS 3.1
La CSP du `SecurityHeadersMiddleware` (`security_hardening.go:76-85`) autorise `script-src 'unsafe-inline'` + `cdn.jsdelivr.net`, ce qui affaiblit la défense XSS. **Correctif** : durcir en même temps que S4-2 (retirer `'unsafe-inline'` sur `script-src`, restreindre les sources).

## Validation d'entrée (observations)

Les handlers du chemin Clean Architecture valident via des DTO + tags `validate:` (ex. bornes `min=0,max=1` sur le score) et retournent des erreurs typées (`ErrValidation` → 400). Aucun montage de requête SQL par concaténation de chaîne n'a été repéré sur le chemin de production (GORM paramétré). Point de vigilance conservé dans la matrice d'isolation (S3-1) : les endpoints de **recherche/export/agrégat** sont ceux où une fuite passe le plus facilement inaperçue.
