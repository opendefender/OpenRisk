# Self-hosting OpenRisk

Self-hosting is a first-class product and our main acquisition channel. The goal:
**one command, works on the first try, zero manual steps.**

A CI job ([`.github/workflows/selfhost-install.yml`](../.github/workflows/selfhost-install.yml))
runs this flow monthly on a fresh Ubuntu 24.04 VM. Be aware that **it has not yet
had a green run** — every run to date has failed, which is how the defects fixed
in #328 went unnoticed. The flow below was verified by hand on a clean stack
(fresh volumes, no `.env`, no keys) on 2026-09-09; treat the CI job as the thing
that will keep it working, not as evidence that it already did.

## Requirements

- Docker Engine + Docker Compose plugin
- `openssl` (for secret/key generation)
- ~2 GB RAM, 2 vCPU, 10 GB disk to start
- Verified clean on **Ubuntu 24.04** and **Debian 12**

## Install (one command)

```bash
curl -fsSL https://raw.githubusercontent.com/opendefender/OpenRisk/master/scripts/install.sh | bash
```

Or from a clone:

```bash
git clone https://github.com/opendefender/OpenRisk.git
cd OpenRisk
./install.sh
```

`./install.sh` at the root is the entry point; it delegates to
`scripts/install.sh`, resolves symlinks, and works from any working directory.

The installer:

1. checks Docker + Compose,
2. generates an **RS256 keypair** (`deploy/selfhost/secrets/`) — the backend
   requires this and its absence is the classic "manual step" we remove,
3. writes a `.env` with **strong random secrets** (DB password, MFA/scanner/audit
   keys),
4. builds and starts postgres + redis + backend + frontend,
5. waits for `/api/v1/health`,
6. **creates the first administrator and prints its credentials.**

It is **idempotent**: re-running keeps your `.env`, your keys and your
administrator account — a second run reports the account already exists rather
than creating another.

App: `http://localhost:3000` · API: `http://localhost:8080/api/v1`.

### The first administrator

The installer ends with something like:

```
[openrisk] Sign in with:
[openrisk]    • Email:    admin@opendefender.io
[openrisk]    • Password: <32 random characters, different on every install>
[openrisk] Change this password on first login. It is stored in deploy/selfhost/.env (0600).
```

The account is created by the backend's own first-boot seeder
(`handler.SeedAdminUser`), which runs only while the users table is empty and
creates the user, an organisation and a root membership — so the account can
actually sign in, rather than existing without a tenant.

The email is **fixed at `admin@opendefender.io`**: the seeder hardcodes it.
Rename the organisation and change the address from inside the app.

The password is 32 alphanumeric characters from OpenSSL's CSPRNG, generated by
the installer into `deploy/selfhost/.env` as `INITIAL_ADMIN_PASSWORD`, alongside
`DB_PASSWORD` and the encryption keys, with the same `0600`. It is **not**
ephemeral — it has to persist, because the backend reads it from the environment
at boot. Change it on first login; after that the value in `.env` is stale and
the app is authoritative.

This compose file requires `INITIAL_ADMIN_PASSWORD` and refuses to start
without it. Outside it (Helm, a hand-written compose file, a bare binary), a
backend started without the variable generates a password itself and writes it
to `INITIAL_ADMIN_PASSWORD_FILE` (default `secrets/initial_admin_password`
under its working directory, mode `0600`); only the path is logged. If that
file cannot be written, the backend stops before creating any account. There
is no default password in any configuration (#485).

An instance first started before that change may still have `admin123` on
this account. The backend logs a `SECURITY WARNING` at every boot while it
does: change the password from the app.

## What a self-hosted instance includes

Self-hosting gives you **the whole codebase**, not a crippled build: there is no
feature flag in this repository that a paid licence unlocks and a self-hoster
cannot. An instance declares itself self-hosted with one environment variable,
read once at boot:

```
OPENRISK_DEPLOYMENT=self_hosted
```

`deploy/selfhost/docker-compose.yml` sets it for you. Every organisation of that
instance then resolves to the **Self-hosted** set (decision D-040): no caps on
users, risks, assets or integrations, and every capability that runs on your own
hardware. The variable is a property of the deployment; no organisation, plan
row or subscription can set it. The variable is required (D-081): without it,
or with a value it does not know, the backend stops at boot and the log names
the variable and its two values. It never guesses, because either guess is
wrong for someone: read as hosted, your install would be capped at Free; read
as self-hosted, the OpenDefender service would be open to every organisation.
### Self-hosted or the OpenDefender service

Every deployment file in this repository is a self-hosted deployment and
declares `self_hosted`: the compose files, the Helm values files
(`helm/values-*.yaml`), the `.env` examples and the CI workflows. Copy any of
them for your own install. The OpenDefender hosted service sets `hosted` from
its own private configuration, which is not part of this repository. No file
here says `hosted`, so none of them can close your instance down to the Free
plan.

The resolution happens in
[`backend/pkg/entitlements/entitlements.go`](../backend/pkg/entitlements/entitlements.go)

### Configuration

Everything lives in `deploy/selfhost/.env` (template: `.env.example`). Notable
optional keys:

- **Payments:** `STRIPE_SECRET_KEY`, `NOTCHPAY_PUBLIC_KEY`, `CINETPAY_API_KEY` +
  `CINETPAY_SITE_ID`. Empty ⇒ Free plan + manual/sales upgrades (no fake URLs).
- **Telemetry:** `OPENRISK_TELEMETRY=off` hard-disables telemetry (see
  [TELEMETRY.md](TELEMETRY.md)). Default: opt-in from the app.
- **Public URL / CORS:** `APP_BASE_URL`, `CORS_ORIGINS`, `VITE_API_URL` when you
  put OpenRisk behind a real domain / reverse proxy.

## Upgrade

```bash
cd OpenRisk
git pull
./scripts/backup.sh                 # always back up first
cd deploy/selfhost
docker compose pull || true         # if using prebuilt images
docker compose up -d --build        # rebuild + restart; migrations run on boot
```

`OPENRISK_DEPLOYMENT` is required from this release on (D-081). The official
`deploy/selfhost/docker-compose.yml` already sets it. If you run your own
compose file or the binary and the backend stops at boot with
`OPENRISK_DEPLOYMENT is not set`, add this line to its environment (or `.env`):

```
OPENRISK_DEPLOYMENT=self_hosted
```

With Helm, `helm upgrade` fails at render time, before any pod restarts, until
`backend.deployment` is set: add `--set backend.deployment=self_hosted`, or put
`deployment: self_hosted` under `backend:` in your values file. The repository's
`helm/values-*.yaml` files already carry it.

Schema migrations run automatically on backend start: GORM AutoMigrate, then
the SQL migrations in `migrations/`, which the backend image carries. The log
shows `migrations: applied successfully (version=N)` once they are in.

Before #1001 the SQL layer never ran on a compose install: it only ran with
`DATABASE_URL` set, and the compose files do not set it. The backend image now
sets `MIGRATIONS_DIR`, and the backend builds the connection from `DB_HOST`,
`DB_USER`, `DB_PASSWORD` and `DB_NAME` itself, so any password works,
spaces, quotes, `@ : / ? # % $` included. In `.env`, write such a password in
single quotes (`DB_PASSWORD='p@ss w#rd$1'`). If it contains a single quote,
use double quotes and escape `"` as `\"` and `$` as `$$`. The
first boot after this upgrade applies the whole chain once on your existing
database. Back up first anyway, as above.

That first pass is written to keep your data. It was replayed on databases
built by earlier releases, and every row was compared before and after. Four
things change on purpose:

- MFA backup codes made by the generator fixed in August 2026 (#240) were the
  same for every user, so anyone could derive them. They are deleted. Codes
  made after the fix are kept. Each person whose codes were deleted gets one
  e-mail, in their language, once the backend is up: their authenticator app
  still works, and new codes come from Settings › Security (turn two-factor
  off, then set it up again). Nobody is mailed twice, even across restarts or
  replicas.
- Assets created before asset categories existed get the category their type
  names (`Server` becomes `server`, `SaaS` becomes `application`). A type with
  no matching category stays uncategorised. Other installs got this when
  categories shipped.
- Residual-risk acceptances recorded before acceptances had an end date get
  one. The acceptance date was not recorded then, so it counts from when the
  risk was last marked mitigated (or last changed): 12 months after that, and
  never less than 30 days from the upgrade, so the owner gets the 30-day reminder before anything expires.
  Acceptances made since already have their date and are left alone.
- Empty fields that the application already reads as a default are filled with
  that default, for example a membership's MFA grace start. This changes no
  screen and no decision.

With several backend replicas (Helm), one replica runs the pass and the others
wait for its lock. A replica can time out on a long first pass, and then it
restarts once. This is expected.

If a migration fails, the backend stops and says so. The data is not touched.
Fix the cause, then mark the last good version:
`docker compose run --rm backend migrate force <version>`.

Your `.env` and `secrets/` are preserved across upgrades.

### Audit hash key (`AUDIT_HASH_KEY`)

Since #879 the backend refuses to boot in production without `AUDIT_HASH_KEY`.
It keys the hash of e-mail addresses in the sign-in audit trail and in the
per-address limits (decision D-065). The log names the variable when it is
missing. New installs get one from `install.sh`. On an install that predates
it, add it once **before** `docker compose up`:

```bash
cd deploy/selfhost
grep -qE '^AUDIT_HASH_KEY=.+' .env || echo "AUDIT_HASH_KEY=$(openssl rand -base64 32)" >> .env
```

Re-running `./scripts/install.sh` does the same. The same goes for `MFA_ENCRYPTION_KEY`
(#1062), which the installer has always generated: an `.env` written by hand
without it gets one, and two-factor secrets encrypted before it existed are
re-encrypted with it at boot. Keep the key: if you change
it, audit entries from before the change can no longer be matched with those
after it, and per-address counters in progress start again (at most one hour,
one day for the sign-up alert). Every replica must have the same key.
During a rolling upgrade, old and new replicas count per-address attempts
separately until the rollout ends.

The same upgrade removes the unkeyed hashes written before it (migration
0079, decision D-074): in the sign-in audit trail they read
`email_sha256=redacted` and the rest of each entry stays; expired password-reset
requests are deleted, and from then on every hour. This cannot be undone. If
you must keep those hashes, back up the database before upgrading.

With Helm, pass it as `--set secrets.inline.auditHashKey=...` (or in your
values file). The chart stores it in the `openrisk-secrets` Secret, and the
render fails without it, so `helm upgrade` stops before any pod restarts.

The MFA key goes the same way: `secrets.inline.mfaEncryptionKey`, stored in the
`openrisk-secrets` Secret rather than in clear in the Deployment (#1057). It is
required (#1062): the render fails without it, and the backend refuses to boot
in production without it or with the public development value. If you never
set one, set any new random secret: at boot, two-factor secrets that were
encrypted with the development key are re-encrypted with yours, and nobody has
to enrol again. A values file that still sets `backend.env.MFA_ENCRYPTION_KEY`
keeps working, and its value moves into the Secret on the next upgrade. Move it
to the new place with **the same value**: once anyone has enrolled two-factor, a
different key cannot decrypt their secrets and they are locked out of it.

`DEVICE_COOKIE_KEY` is optional (Helm: `secrets.inline.deviceCookieKey` and
`deviceCookiePreviousKey`; compose: `.env`). It signs the cookie that lets a browser
which already signed in get past a sign-in lock someone else keeps setting
(D-064). Without it, the key is derived from `AUDIT_HASH_KEY`. Set it to
rotate the cookie key on its own, with the old value in
`DEVICE_COOKIE_PREVIOUS_KEY` until the cookies signed with it age out (90
days); changing it without that untrusts every browser, which then waits out
a lock like any other.

### Password hashing

Passwords are stored with Argon2id. The defaults are 64 MiB of memory,
3 iterations and 4 lanes. Each sign-in holds that memory while it runs, and
at most `ARGON2ID_MAX_CONCURRENT` hashes run at the same time; the others
wait their turn. On a small machine you may want to lower the cost:

```bash
ARGON2ID_MEMORY_KIB=65536    # minimum 19456
ARGON2ID_TIME=3              # minimum 2
ARGON2ID_PARALLELISM=4       # 1 to 255
ARGON2ID_MAX_CONCURRENT=4    # minimum 1
```

The backend refuses to start if a value is not a number or is below its
minimum. Every hash stores its own parameters, so changing them never breaks
an existing password. When you raise them, each account is rehashed with the
new values at its next sign-in. The Helm chart gives the API 1 CPU and 1 GiB
for this reason.

Instances installed before June 2026 may still hold passwords stored as
unsalted SHA-256. Those accounts cannot sign in, even with the right
password: their owners have to use "Forgot password?", which stores the new
one with Argon2id.

To see how many are left, watch
`openrisk_password_hash_accounts{algorithm="sha256_legacy"}` in Prometheus,
refreshed every hour. `state="active"` counts accounts that still have to
reset. `state="deleted"` counts soft-deleted accounts, which will never reset
and keep their old hash until the row is purged.
`openrisk_password_hash_upgrades_total` counts passwords rehashed at sign-in
after a cost increase.

## Backup & restore

```bash
./scripts/backup.sh                 # → backups/openrisk-backup-<stamp>.tar.gz
./scripts/restore.sh backups/openrisk-backup-<stamp>.tar.gz
```

The tarball contains the Postgres dump, the `secrets/` (encryption keys) and the
generated data exports. **Store it off-box** — it holds your keys. Restore
overwrites the current database and secrets.

## ARM64 (AWS Graviton, Apple Silicon, Raspberry Pi)

Base images (`postgres`, `redis`, `alpine`, `golang`) are multi-arch, so the
stack builds and runs natively on ARM64 — `./install.sh` works unchanged
on a Graviton VM. To build and publish a multi-arch image:

```bash
# The backend builds from the repository root: its image carries migrations/.
docker buildx build --platform linux/amd64,linux/arm64 \
  -t openrisk/backend:latest -f backend/Dockerfile . --push
docker buildx build --platform linux/amd64,linux/arm64 \
  -t openrisk/frontend:latest ./frontend --push
```

## Kubernetes (Helm)

A maintained chart lives in [`helm/openrisk`](../helm/openrisk) with
`values-dev.yaml` / `values-staging.yaml` / `values-prod.yaml`. It schedules on
ARM64 nodes when you provide ARM64 images (above). Provide the same secrets
(`RSA_*`, `MFA_ENCRYPTION_KEY`, `SCANNER_CREDENTIAL_KEY`, `AUDIT_EXPORT_KEY`) and
optional payment/telemetry env via the chart's `values` / a `Secret`.

`backend.deployment` has no default and the render fails without it (D-081).
The repository's values files set it to `self_hosted`; with your own values
file, pass it explicitly:

```bash
helm install openrisk ./helm/openrisk -f my-values.yaml \
  --set backend.deployment=self_hosted
```

See [Self-hosted or the OpenDefender service](#self-hosted-or-the-opendefender-service).

## Integrations on a private network

Scanner connectors (Nessus, Qualys, Defender…) and ITSM ticketing (Jira,
ServiceNow) call the `base_url` a tenant configures. By default those calls only
reach **public** addresses over **https**: private (RFC 1918, ULA), carrier-grade
NAT, loopback and link-local addresses — which include the cloud metadata
endpoints — are refused, both when the URL is saved and again when the
connection is opened.

If your tools run on your own network, open their ranges explicitly:

```bash
OUTBOUND_ALLOWED_CIDRS=10.20.0.0/16,192.168.50.0/24
```

Loopback (`127.0.0.0/8`, `::1`) and link-local (`169.254.0.0/16`, `fe80::/10`)
stay denied whatever the list says. A malformed entry stops the backend at
startup. These requests do not go through `HTTP(S)_PROXY`, and redirects are
only followed on the same host.

Do not add the NAT64 prefix (`64:ff9b::/96`) to the list: it embeds IPv4, so
opening it re-opens every IPv4 address behind the translator, loopback and
metadata included.

The same rule covers the discovery connectors that run inside the backend:
Kubernetes (`api_server`), Docker (`host`), VMware vCenter (`url`), Active
Directory (`url`, `ldap://` or `ldaps://` only) and GitHub / GitLab (`base_url`).
A cluster, vCenter or domain controller on your own network needs its range in
`OUTBOUND_ALLOWED_CIDRS`.

A Docker `host` that names a unix socket (`unix:///var/run/docker.sock`, or a
bare path) is refused unless you set:

```bash
SCANNER_DOCKER_SOCKET_ENABLED=true
```

Turn it on only if you mount a Docker socket into the backend on purpose. Any
organisation that can create scan configs can then read that daemon's
containers and images.

### Kubernetes: the cluster's certificate

A Kubernetes scan config verifies the API server's certificate. Put the
cluster's CA in the config's `ca_cert` credential (PEM) — this is the right
answer for a self-signed cluster, and it pins the scan to that cluster.

Without a `ca_cert`, the certificate is checked against the system roots. A
self-signed cluster then fails with a certificate error. Setting the credential
`insecure` to `true` skips the check, exactly as the vCenter connector's
`insecure` does. Avoid it: the scan carries the ServiceAccount token, and
anything on the path between the backend and the API server can take it.

## Troubleshooting

- **Backend restarts / "RSA keys required":** the `secrets/` keypair is missing —
  re-run `./install.sh` (it regenerates only what's absent).
- **Port already in use:** set `BACKEND_PORT` / `FRONTEND_PORT` in `.env`.
- **Logs:** `cd deploy/selfhost && docker compose logs -f backend`.
